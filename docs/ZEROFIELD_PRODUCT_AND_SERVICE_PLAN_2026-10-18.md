## 1. 核心定位

ZeroField 是建構於 Comfy Developer Platform 的開源多代理製片協作工作台。它把角色資產、分鏡、鏡頭控制、生成任務與修改紀錄，組織成可追蹤、可審核、可重製的專案流程：

**企劃 → 資產準備 → 拆鏡 → 多代理交辦 → 生成與進度追蹤 → 看片標註 → 修改或重拍 → 挑選版本。**

延續 OpenBench 的核心：文件、表格、畫廊、流程圖、多人權限與多代理分工共同服務一個專案。使用者可以從整體企劃一路追到單鏡素材、生成參數與修改原因。

主要候選情境是 AI 短劇製作；廣告批次變體可作為第二種輕量模板。最終比賽主線仍須依工作流實測結果收斂，研究範圍包含 Higgsfield 整站，不限 Genjutsu。

## 2. 問題與競品觀察

### 大量素材與反覆生成的管理成本

一個多鏡頭專案需要持續處理角色、場景、道具、風格、聲音、參考影片與多個 Take。研究假設是：重複挑選素材、搬運設定、辨識版本與交代修改，會成為製作瓶頸。

貼文提及「553 次生成、608 個素材、298 支影片」的案例數字，本輪未取得對應畫面核對；先保留為待驗證的需求背景，不轉寫成操作次數、節省比例或市場普遍結論。

### Higgsfield 同時提供模型與製作流程

全站盤點顯示，Higgsfield 已有角色與風格資產、分鏡工具、Cinema Studio、影片修改、廣告工作流、Canvas、Supercomputer 及外部軟體整合。AI 協助拆鏡、並行工作流與並排比較已有相應產品能力。

因此，ZeroField 的差異需要落在可展示的使用流程，例如資產自動綁定、清楚的交辦與審核紀錄、可重現的生成設定、修改前後追蹤，以及多人協作的完整閉環。這些是待驗證的產品價值，不能先宣稱優於所有競品。

### 結構化控制可成為代理操作介面

Cinema Studio 的運鏡介面明示：選項會按順序插入 Prompt。這支持把相機、運鏡與風格整理成結構化欄位，再編譯為工作流輸入的設計方向。

這項觀察不代表已還原 Higgsfield 全部控制器或底層模型，也不保證替換模型後仍有相同效果。各控制維度仍需測試輸出是否有可辨識、可重複的差異。

## 3. 五大核心服務

| 服務 | 使用者與代理的操作方式 | 預期價值 |
| --- | --- | --- |
| **Asset Hub & Auto-Binding** | 統一管理 Character、Location、Prop、Style、Audio；分鏡與修改指令以 `@CAST-01`、`@LOC-01`、`@PROP-01` 引用，執行時解析對應素材與外觀設定。 | 減少重複選圖，明確記錄每鏡使用的素材。 |
| **Shot & Style Compiler** | 專案／場次設定 Genre、Era、Tempo、Palette、Lighting；單鏡設定 Camera、Lens、Aperture 與有序 Movement。代理批量填寫，人類可用快速選單調整。 | 讓整場戲繼承共同風格，並保留單鏡控制。 |
| **Crew Orchestration & Multi-Take Review** | Showrunner、Screenwriter、Cinematographer、Continuity QA 分工；支援多列交辦與關鍵鏡頭的 2–3 個候選版本。 | 追蹤任務進度，支援版本比較與人工選片。 |
| **Video Review & Revision Loop** | Table／Gallery 格內看片、標註、交辦修改；保留原有資產綁定，修改指定參數或重新生成。 | 把審片意見連回明確的鏡頭、版本與執行任務。 |
| **Comfy Execution & Workflow Inspection** | 透過 Comfy Developer Platform 執行，保留本機 ComfyUI 相容性；檢視實際參數、工作流及生成紀錄。 | 提供可理解、可重現的執行依據。 |

多代理提案競速與媒體 Take 比較是兩種不同操作。規劃中的 Multi-Take Review 需要確認是否已有對應的媒體版本、同步播放與選片資料模型，不能僅以既有提案 Race 視為完成。

## 4. 三條核心生成工作流

原文先寫「四類服務」，實際列出三類；本整理統一為以下三條生成工作流，與上面的五大產品服務分開描述。

| 工作流 | 輸入 | 輸出 | 驗證重點 |
| --- | --- | --- | --- |
| **資產與分鏡首幀** | 文字、角色／場景／道具參考、風格設定 | 資產基準圖與分鏡首幀 | 外觀一致性、引用正確性與重跑紀錄；候選採 FLUX 開放權重工作流。 |
| **結構化鏡頭生成** | 首幀／參考素材、Film Setup、Camera、Lighting、有序 Movement | 動態鏡頭與適用的聲音輸出 | 控制指令是否有效、鏡頭品質與音畫表現；核心候選為 LTX-2.5。 |
| **影片重製與局部修改** | 原片、目標角色／道具參考、修改指令、必要控制資料或遮罩 | 重製片／修改片與對照 | 動作時機、角色外觀、背景、遮擋與原音保留；技術路線須先實測。 |

第三條的首個候選基準為：**將單人原片中的角色換成指定原創角色，檢查動作、背景與原音軌的保留程度。** Depth／Pose、SAM2 遮罩及音軌接回方式，均屬候選技術，不代表已驗證可行。

原音接回與音畫同步要分別檢查；角色一致性也不能只靠「鎖定 Seed」視為達成。未通過驗證的效果不放進已交付能力或預設展示承諾。

## 5. 資料與模板設計提案

### 專案結構

| 分頁 | 用途 | 建議內容 |
| --- | --- | --- |
| `director-brief` | 全片與場次企劃 | 劇本、Genre、Era、Tempo、Palette、Lighting、共同限制。 |
| `soul-cast` | 專案資產中心 | Asset ID、Category、Name、Locked Appearance Prompt、Seed、Reference Media、Audio／Voice Profile、Status、Notes。 |
| `cinema-studio` | 多鏡頭導演台 | Shot、References、Film Setup & Lighting、Camera & Ordered Movement、Scene & Action Prompt、Keyframe、Cinema Shot、Status、Director Notes。 |
| `openjutsu-lab` | 影片重製與修改 | Clip ID、Mode、Source Video、Target References、Edit Prompt、Remastered Video、Comparison Output、Status、Notes。 |
| `comfy-pipeline` | 可檢視執行流程 | 資產／首幀、鏡頭生成、修改、輸出與審核節點。 |

欄位為概念提案，尚未決定如何遷移現有資料。外觀描述與 Seed 應可分辨；Reference、來源影片與目標素材應能明確區分角色。欄位名稱、畫面、預載專案與角色職稱依現有規範使用英文。

### 兩種候選專案模板

- **Short-form Drama Studio**：Brief → Cast／Locations／Props → Storyboard → Cinema Shots → Review／Retake → 必要的 V2V 修改。
- **Ad Variation Studio**：原片／商品 → Avatar、Product、Hook、CTA 變體列 → 批次生成 → 比較與挑選。可用少量列展示同一套協作架構的重用能力，不預先擴成另一套大型產品。

Ad Multiplier 的「最多 20 張參考圖」是輸入限制，不能寫成「一次必定生成 20 個版本」。變體數量應由我們實際支援的任務與預算決定。

## 6. 四階段交付順序

### 階段一　影片基礎能力

讓工作台能可靠地接收、預覽與重拍短片。

- 瀏覽器上傳 MP4／WebM，單檔上限 64 MB。
- `/meta` 只取 metadata，不為查詢大小載入影片 Blob。
- 資產路由具備 ETag／304、Range／206 及既有規格要求的磁碟快取。
- 格內 `<video controls muted loop playsInline preload="metadata">`；緊湊列表按需播放，移開即暫停。
- 前端 metadata 快取與影片重新生成入口。

驗收：能上傳、格內預覽、拖曳播放時間與發起單鏡重拍；確認 metadata 路由沒有讀取完整影片內容。

### 階段二　資產綁定與鏡頭編譯

讓表格內容成為可執行輸入。

- 解析當前分鏡的 `@Asset` 引用，取得指定素材及鎖定描述。
- 專案／場次預設與單鏡覆寫的繼承規則明確。
- 相機、光學、燈光與有序運鏡編譯成工作流接受的參數或 Prompt。
- 代理可批量填寫；人類可用輕量選單修改。

驗收：不同鏡頭不會誤用其他列的素材；修改單鏡設定後，其餘綁定維持正確；可查看解析與編譯結果。

### 階段三　Comfy 平台與實測工作流

- 整合 Comfy Router 和／或 Comfy SDK，確認符合比賽的平台要求。
- 支援角色／場景多參考圖、來源影片及參數綁定。
- 依序跑通資產／首幀、鏡頭生成、影片重製三條候選流程。
- 記錄實際使用的模型、版本、節點、輸入輸出、耗時、失敗情況與可重跑設定。

驗收：工作流可由其他人依說明執行；有真實輸出證據；已知限制清楚，不以介面存在代替生成成功。

### 階段四　展示專案與啟動體驗

候選示範故事為 **The Last Signal**，所有素材使用原創或已授權內容。

- 預載主角、配角、雨夜天文台、關鍵道具與設定。
- 規劃 6–8 鏡真實首幀與影片；部分 Approved，部分 Pending Review 並附導演意見。
- 若影片重製通過實測，再放入 1–2 組原片／修改片對照。
- `run_studio.py` 啟動 Server 與 Worker，載入展示專案，清楚說明環境與模型需求。

驗收：評審可以從預載成品體驗「看片 → 標註 → 交辦 → 比較 → 選片」。預載展示與現場重新生成所需的 GPU、模型、網路或憑證要分別說明，不能承諾任何電腦皆免配置執行。

## 8. 範圍邊界與既有規格的關係

規劃以重用現有協作架構為原則，避免新增完整時間軸剪輯器、複製大量獨立工具頁，或把未測過的特效寫成已完成能力。

| 議題 | 整理後的處理方式 |
| --- | --- |
| 開放權重與 Partner Models | 官方一般組別允許 Partner Models，但本 Repo 的既有規範要求純開放權重。路由抽象不代表已授權加入閉源 API；本文件保留現有限制。 |
| FFmpeg 並排對比 | 原文後段建議只在網頁並排播放；現有規格仍要求 `side_by_side` 對比 MP4 與 `+faststart`。網頁比較可並存，不能據此視為已刪除原交付要求。 |
| LTX 重製能力 | Motion Transfer／Object Swap 為待驗證能力。LTX 作為核心影片模型的競賽方向，不等於已具備 Genjutsu 等效品質。 |
| 工作流檔名 | 原文提出的三個新名稱是候選；與現有規格中的檔名不同，實作前需統一，避免兩套相同流程。 |
| 前端與狀態規範 | 沿用英文介面、前後端狀態同步與後端舊狀態相容要求；改動 `ui/src/` 後仍須執行 `npm run build --prefix ui`。 |
| 時程 | 原文「12 天」是當時的估計，不是排程承諾；工期需依現況查核、模型測試與比賽截止時間重排。 |

適用的現有規範：[設計與開發規範](DESIGN_AND_DEV_GUIDELINES.md)、[ZeroField 規格](ZEROFIELD_SPEC.md)、[多代理規格](AGENT_ORCHESTRATION_SPEC.md)。

## 9. 進入實作前要收斂的事項

1. 決定比賽示範主線：短劇製作是否為主要交付，廣告變體是否只保留輕量範本。
2. 查核現有能力與缺口，區分已完成、可重用、需要修正與新增項目。
3. 定義 `@Asset` 的識別、素材角色、繼承與失敗處理規則。
4. 選定 Comfy 平台接入方式，保持 Repo 的開放權重限制。
5. 先驗證三條候選工作流，尤其影片重製的品質邊界。
6. 區分代理提案比較與媒體 Take 比較，確定導演如何選片及回寫狀態。
7. 統一欄位、工作流檔名、展示內容與並排對比輸出要求後，再形成可執行的工程清單。
