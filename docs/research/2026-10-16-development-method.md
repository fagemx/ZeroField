# 從既有平台開發紀錄學到的方法

2026-10-16。使用者授權唯讀研究指定私人平台的開發過程。本文件只保留去識別化的方法，不收錄私人業務、帳號、原始程式、內部產品命名或部署設定。

## 讀過什麼、能證明什麼

- 原始 phase roadmap：先把反覆發生的工作、角色、資料來源和交接循環畫出來，再安排基礎建設。這是規劃紀錄，不等於已驗收。
- `.edda/branches/main/log.md` 的決策條目：有產品入口、界面簡化、原先規劃被推翻與後續裁定。大量 session digest 只有工具次數，不能當作完整逐字對話。
- 2026-10-13／14 的設計與 Git 修訂：先定具體使用者卡住的地方及助理入口；實作期間新增的使用者要求回寫設計，包括操作入口、可見範圍、按需提供輸出、完成後的提示。
- `design-qa.md` 與 `designops-design-qa.md`：保存指定參考圖、實際畫面、視窗尺寸、逐輪問題、修正與仍接受的差異。有版面太高、標題換行、控制太重、窄視窗內容被擠走等具體修正。
- 開發／發布生命週期文件：版本、build、行為檢查、回復方案與正式部署分開；HTTP 成功或重啟本身不等於畫面可工作。

以上是決策日誌、Git 修訂與 QA 文件的抽樣研究，沒有聲稱已讀完所有聊天或驗證該平台今日狀態。

## 值得複製的開發過程

| 過程 | 為何有效 | OpenBench 的落地方式 |
| --- | --- | --- |
| 先寫一段真實工作故事 | 明白使用者要交出什麼，減少按工程模組拼 UI | 同時描述辦公整理、美術審核、組裝任務三段工作；共同操作只設計一次 |
| 找卡住的位置 | 工具不要求使用者離開工作去尋找功能 | 選取儲存格後就能編輯／交給代理；選節點即可看輸入、操作、輸出與錯誤 |
| 提出有差別的方案 | 討論針對具體取捨，而非「喜不喜歡」 | 表格直接編輯與詳情面板如何分工；畫布與設定如何同屏；Excel 原檔與結構化表的邊界 |
| 先看連貫畫面與狀態 | 好看的首屏不能證明下一步好操作 | 每個方案至少呈現空白、工作中、結果核對、出錯恢復四種狀態 |
| 使用者修正回寫決策 | 後續代理不把已否決方案重新做回來 | 每次記錄原假設、使用者回饋、改動與受影響範圍；最新決策覆蓋舊施工清單 |
| 先比較再施工 | 功能實作不能替代元件與互動適配研究 | 用相同選取／貼上／撤銷任務比較成熟 grid；用同一流程比較節點設定／試跑體驗 |
| 實作後做視覺與操作 QA | 看得到密度、焦點與交接成本 | 同視窗尺寸比較設計與實作，走完整操作，記錄多餘動作、誤操作、資料理解與恢復 |
| 使用一段時間後修訂 | 單次順利不代表每天都好用 | 分開評估首次使用與第二次使用；三類工作都要重複，不以展示數量算成熟度 |

## 對目前作法的修正

先前「開源能力表 → 三視圖 → 立刻加 UI」跳過了操作設計及需求邊界，施工次序已撤回。三視圖可作日後需求，但不能替代表格基本編輯、選取、撤銷、欄位調整，也不能解決流程輸入輸出的理解負擔。

下一輪的討論單位應該是一段工作與連貫畫面，不是「是否增加 Gallery」這種單獨功能。下一輪交付也不應只是新的長篇施工清單，而要有具體互動方案、取捨、仍需使用者決定的問題，以及每個問題會改變哪個設計。

## 問題怎麼問才有用

先由研究提出建議與可見後果，再請使用者修正。例如：

- 匯入 Excel 後需要新增欄位，但原檔保真不能涵蓋這項操作：畫面應如何先說清楚、如何交付新檔，才不會做到最後才失敗？用實際匯入／改欄／匯出畫面比較。
- 連續修改十個欄位：日常動作留在格子內；長文、媒體與紀錄放側面。展示連續操作與鍵盤移動，請使用者指出不符合工作習慣之處。
- 組裝一個流程：從「讀取資料 → 處理 → 核對 → 寫入」開始，每一步展示選擇資料、看到樣本、試這一步的過程。再討論多人審核與複雜分支，而不是先要求填滿所有工程設定。

這些問題應隨具體設計出現，不再要求使用者從三種工作裡挑一種，也不把所有底層選型丟給使用者。
